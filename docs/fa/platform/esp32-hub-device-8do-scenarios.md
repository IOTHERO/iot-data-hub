# هاب مرکزی با DEVICE 8DO (Relay-8): فهرست سناریو و کارهای لازم

> برای دادن به سامانهٔ DEVICE 8DO: «هاب این‌ها را از ماژول می‌خواهد؛ در Firmware ماژول لحاظ کن».
> هاب: `firmware/esp32-hub`. ماژول: پروژهٔ `TiTiRelay8`. تگ‌های ماژول همان `relay_1`..`relay_8` و `uptime_s` است.

## ۱. اتصال ماژول به هاب (تنظیم ماژول)

| تنظیم در پورتال ماژول | مقدار |
|---|---|
| حالت | شبکه / MQTT (کابل LAN با W5500 یا وای‌فای؛ «نوع شبکه» = خودکار) |
| سرور ۱ (پروتکل «پلتفرم TiTiSwitch») | آدرس IP هاب، پورت `1883`، **بدون TLS**، پیشوند تاپیک **خالی** |
| نام کاربری / رمز | `device_id` / `device_secret` همان ماژول (هاب باید همین‌ها را در فهرست داشته باشد، یا پنجرهٔ ثبت ۲ دقیقه‌ای باز باشد) |
| سرور ۲ (اختیاری) | سرور اصلی، برای وقتی ماژول مستقیم کار می‌کند |
| نشانی HTTP هاب (`apiUrl`) | **خالی**: هاب ESP این مسیرها را ندارد؛ قاعده و کلید را از راه MQTT (`config` و `rules`) می‌دهد |

هاب فقط ماژولی را می‌پذیرد که در فهرست باشد (یا در پنجرهٔ ثبت): ثبت خودکار = کلید کانفیگ هاب ۳ ثانیه ON، یا دکمهٔ «ثبت ماژول جدید» در پورتال هاب.

## ۲. آنچه هاب از ماژول می‌خواهد (لطفاً در Firmware پشتیبانی شود)

1. **telemetry کامل بلافاصله پس از اتصال** (حداکثر ۲ ثانیه) و **دوره‌ای هر ≤ ۳۰ ثانیه**. هاب ماژول را بعد از ۹۰ ثانیه سکوت «قطع» می‌داند (قابل تنظیم). تغییر هر رله هم فوراً.
2. **`state` با `local_addr` و `firmware`** (retained، با LWT) مثل حالا.
3. **ack سه‌مرحله‌ای** (`received` ← `done` / `failed`) با `command_id`؛ دلیل‌های `failed` مثل حالا. هاب دستور تکراری را دوبار نمی‌فرستد ولی اگر فرستاد، فقط پاسخ دوباره بدهید.
4. **ساعت از هاب (مهم برای حالت آفلاین) — در Firmware 8DO پیاده شد:** ماژول RTC ندارد و بدون اینترنت NTP ندارد. هاب بعد از هر وصل شدن و هر ۶ ساعت روی `d/<id>/config` این پیام را می‌فرستد:
   **`{"type":"time","server_time":"<ISO UTC>","utc_offset_min":210}`**.
   لطفاً پیام `type = "time"` را بپذیرید، ساعت را از آن تنظیم کنید و نوع ناشناخته را نادیده بگیرید. با این، `expires_at` فرمان‌ها و قواعد زمانی ماژول هم بدون اینترنت کار می‌کند.
5. **تگ‌های اضافهٔ مفید برای داشبورد هاب** (اختیاری): `rssi`، `reset_reason`، `boots`، `heap`.
6. **فرمان «شناسایی»** (چشمک LED برای پیدا کردن ماژول): تگ `identify` — در Firmware 8DO پیاده شد. هاب می‌تواند هر تگ را با API فرمان بفرستد (دکمهٔ پورتال بعداً).
7. **رفتار هنگام قطع هاب:** همان «اقدام هنگام قطع ارتباط» (حفظ / خاموش / از پیش تعیین‌شده). برای ساختمان: پیشنهاد **«حفظ وضعیت»**، تا ریست یا قطع شدن هاب رله‌ها را نپراند.
8. **ماژول قواعد آفلاین خودش را فقط هنگام قطع هاب اجرا کند** (همان `offline_after_s`)؛ برنامهٔ اصلی روی هاب است. قاعدهٔ تکراری روی ماژول و هاب هر دو نباشد.
9. **اتصال دوباره:** همان قاعدهٔ قرارداد (۰..۱۰ ثانیه تصادفی، دو برابر تا ۵ دقیقه، ±۲۰٪). پس از قطع برق ساختمان هاب و ماژول‌ها هم‌زمان بالا می‌آیند: ماژول باید صبر کند و دوباره تلاش کند (هاب چند ثانیه دیرتر بالا می‌آید).
10. **حداکثر ۴ پیام در ثانیه** (همان حالا).

## ۳. سناریوهای آماده که هاب روی 8DO اجرا می‌کند

نام کوتاه ماژول در هاب (`m1`) در فرمان‌ها استفاده می‌شود. همه روی خود هاب اجرا می‌شوند، با اینترنت یا بدون آن.

| # | سناریو | ماشه | اقدام |
|---|---|---|---|
| ۱ | روشن شدن چراغ‌ها در شب | زمان `18:30` | `m1.relay_1` روشن |
| ۲ | خاموشی شبانه | زمان `23:30` همهٔ روزها | رله‌های ۱ تا ۸ خاموش |
| ۳ | آبیاری | زمان `06:00`، روزهای شنبه/دوشنبه/چهارشنبه | `relay_5` روشن ← تأخیر ۱۸۰۰ ثانیه ← خاموش |
| ۴ | چشمک / پالس تکرارشونده | هر ۶۰ ثانیه | `relay_3` روشن ← تأخیر ۲۰ ← خاموش |
| ۵ | درب‌بازکن (لحظه‌ای) | دستی (گوشی/پیامک) | `relay_2` با `pulse_s: 1` |
| ۶ | تمام خاموش | دستی | رله‌های انتخاب‌شده خاموش |
| ۷ | حالت «بیرون از خانه» | دستی | چند رله خاموش + `relay_7` (آژیر یا چراغ) روشن |
| ۸ | شرط روی مقدار | `relay_1` روشن شد (`for_s: 7200`) | بعد از ۲ ساعت `relay_1` خاموش (محافظ فراموشی) |
| ۹ | اینترلاک نرم‌افزاری | دستی | اول رلهٔ مقابل خاموش ← تأخیر ۱ ← رلهٔ مورد نظر روشن (ماژول خودش هم اینترلاک دارد) |
| ۱۰ | قطع ماژول | رویداد `module_offline` | پیامک «Module offline» + هشدار روی LED ALARM |
| ۱۱ | قطع اینترنت | رویداد `cloud_lost` | هشدار؛ اقدام ایمنی (مثلاً روشن ماندن چراغ پارکینگ) |
| ۱۲ | برگشت اینترنت | رویداد `cloud_back` | پاک شدن هشدار، گزارش اجرای سناریوها به سرور |
| ۱۳ | ماژول برگشت | رویداد `module_online` | برگرداندن وضعیت دلخواه (مثلاً `relay_1` روشن) |

## ۴. راه‌های کنترل ماژول از هاب

1. **پورتال هاب** (صفحهٔ «ماژول‌ها»): دکمهٔ هر رله، زنده.
2. **اپ فلاتر** از راه API محلی هاب: `POST /local/v1/command` با `tag = m1:relay_3` و `value_json = true`.
3. **پیامک:** `HUB 1710000001 m1.relay_1=1 m1.relay_2=0 <امضا>`.
4. **سرور** (آنلاین): پیام `down` با `type: "cmd"` و `d: "<device_id>"`.
5. **سناریو و زمان‌بندی** روی خود هاب.

## ۵. چیزهایی که برای هماهنگی لازم است

- ماژول `device_id` و `device_secret` را از سامانهٔ تولید دارد؛ همان‌ها در فهرست هاب وارد می‌شود (پورتال هاب، API محلی `modules:put` یا پیام `registry` از سرور). اگر شناسه یکتا نباشد هاب رد می‌کند.
- نام کوتاه (`alias`) در هر هاب یکتا است (حروف کوچک و عدد، تا ۸ نویسه).
- ماژول در حالت RS-485/Modbus هم پشت هاب کار می‌کند: هاب Modbus Master دارد (`rs485.cpp`). در فهرست ماژول‌های هاب برای آن «آدرس RS-485» (`rtu`) بگذارید؛ رمز لازم نیست. سرور آن را مثل بقیه می‌بیند (از راه `h/<hub>/up`).
- هر هاب تا ۳۲ ماژول و ۲۴ سناریو؛ هر ماژول تا ۱۶ تگ.
